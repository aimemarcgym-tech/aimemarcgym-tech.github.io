Architecture de référence — appli UFOLEP GAF

Résumé de l'architecture d'une PWA de gestion de compétitions et d'entraînements de gymnastique (fédération UFOLEP, section GAF), à donner à une nouvelle session Claude pour démarrer un projet FFG séparé sans repartir de zéro.

Principe fondateur — à réappliquer quelle que soit la fédération

Ne jamais inventer de donnée réglementaire. Tout ce qui n'est pas fiablement vérifiable dans les documents officiels doit être marqué « ⚠ à confirmer » plutôt que deviné. C'est la règle la plus importante du projet — elle évite qu'un coach note mal une gymnaste en vrai à cause d'une donnée fausse.

01Stack technique

  • Next.js 16 (App Router), TypeScript, React 19, Tailwind CSS v4.
  • Export statique (output: "export", trailingSlash: true) — appli 100 % cliente, aucun serveur Next en prod. Hébergée sur GitHub Pages via un dossier docs/ synchronisé à chaque build.
  • PWA : service worker généré après le build, précache tous les assets, fonctionnement 100 % hors-ligne une fois visité en ligne. Détection de nouvelle version avec bannière « Actualiser » plutôt que rechargement forcé en pleine saisie.
  • Firebase Auth + Firestore pour les données « légères » (texte/structure), synchronisées entre appareils d'un même compte coach.
  • IndexedDB (librairie idb) pour le binaire lourd (musiques, photos, vidéos) — volontairement non synchronisé dans le cloud, pour éviter les coûts de stockage à l'échelle. L'export/import JSON manuel sert de sauvegarde/transfert.

03Le moteur de règlement data-driven

C'est le design le plus important à reproduire pour la FFG, même si les données changent entièrement. Les règles ne sont jamais codées en dur dans les composants : chaque exigence a un id mappé vers un CheckSpec typé, évalué génériquement. 

type CheckSpec =
  | { type: "CATEGORY_COUNT"; category: string; min: number; branch?: string }
  | { type: "ELEMENT_AT_PALIER_MIN"; palierMin: Palier; category?: string; min?: number }
  | { type: "SALTO_AT_PALIER_MIN"; palierMin: Palier }
  | { type: "TWO_ACRO_DIFFERENT_DIRECTIONS" }
  | { type: "LIAISON_ACRO"; runMinLength: number; runsNeeded: number }
  | { type: "FORCE_OR_PG" }
  | { type: "NAME_CONTAINS_ALL"; terms: string[]; min?: number }
  | { type: "MANUAL" }; // confirmation manuelle du coach

engine/composition.ts expose evaluateCheck(apparatus, spec, elements, context), générique pour tous les types ci-dessus. Ajouter une nouvelle règle = ajouter un cas au union type + un cas dans le switch, sans toucher aux données existantes.

Contexte tronc commun / valorisation

context: "TRONC_COMMUN" | "VALORISATION" — certains paliers (ex. « Prérequis ») comptent pour le tronc commun mais jamais pour une valorisation ; le moteur exclut certains éléments du set « utilisable » selon le contexte d'évaluation, jamais au niveau des données.

Éléments cross-listés

Piège identifié et corrigé dans ce projet

Un même élément qui compte dans deux catégories (ex. une sortie qui compte aussi comme acro) se modélise via extraCategories?: string[] sur l'élément — jamais en dupliquant la ligne JSON avec le même code. Dupliquer casse les clés React et les Map indexées par code.

Suggestions (« Assistant »)

computeSuggestions() simule l'ajout de chaque élément candidat non utilisé et compare avant/après sur chaque exigence manquante — permet de dire « ajouter X complète l'exigence Y » sans logique spécifique par exigence.

Import des données réglementaires

Transcrites à la main depuis des PDF/tableaux officiels, avec verified: true/false et sourcePage pour tracer la provenance. Ne jamais deviner une valeur manquante — la laisser absente et flaguer.

04Firestore — structure

users/{uid}/
  clubs/{id}
  gymnasts/{id}            (+ passageOrder, musicOrder, homeOrder)
  gymnastSkills/{id}        statut de maîtrise par élément et gymnaste
  movements/{id}
  movementElements/{id}
  movementSnapshots/{id}    historique horodaté
  trainingSessions/{id}     journal, par gymnaste OU par équipe
  meta/migration            migration one-shot IndexedDB → Firestore

shares/{shareId}            collection PUBLIQUE séparée — instantanés figés
                            pour le partage par lien sans compte

Règles de sécurité :

match /databases/{database}/documents {
  match /users/{uid}/{document=**} {
    allow read, write: if request.auth != null && request.auth.uid == uid;
  }
  match /shares/{shareId} {
    allow read: if true;
    allow create: if request.auth != null && request.resource.data.ownerUid == request.auth.uid;
    allow update, delete: if request.auth != null && resource.data.ownerUid == request.auth.uid;
  }
}

src/lib/data.ts centralise toutes les opérations Firestore derrière des fonctions nommées (getGymnasts, createMovement, saveMovementElements…) — jamais d'accès direct depuis un composant. Helpers internes col()/docRef() scopent automatiquement sur users/{'{uid}'}/...

05Partage par lien public

  • createShare(type, data) écrit un instantané figé (pas une référence live) dans shares/{'{id}'} ; getShare(id) le relit publiquement.
  • AuthGate.tsx laisse passer les routes /partage/* sans vérifier la connexion, et n'affiche pas la nav.
  • Chaque type a son propre payload typé et sa propre page publique de lecture.
  • Pièces jointes (PDF…) encodées en base64 dans le document Firestore, plafonnées pour rester sous 1 Mo/document.

06Sauvegarde manuelle

src/lib/backup.ts exporte tout (Firestore + IndexedDB) en un seul JSON téléchargeable, et sait le réimporter. downloadBackup() utilise showSaveFilePicker (File System Access API, Chrome/Edge desktop) pour laisser choisir l'emplacement, avec repli sur téléchargement classique sinon.

07Glisser-déposer

useDragReorder.ts : réordonnancement par Pointer Events (pas l'API HTML5 Drag and Drop native, qui ne marche pas sur mobile tactile). Capture du pointeur dès pointerdown, position des éléments mesurée une seule fois au début du drag pour éviter un reflow forcé à chaque pointermove. DragHandle.tsx = poignée standard (zone tactile 40×40).

08Conventions de code

  • Un fichier par composant dans src/components/, pas de sous-dossiers, pas de barrel index.ts.
  • Commentaires réservés au pourquoi non-évident — jamais pour décrire ce que fait le code.
  • Pas d'abstraction prématurée : dupliquer 3 lignes plutôt qu'abstraire pour un seul appelant.
  • TypeScript strict, npx tsc --noEmit après chaque changement.
  • Déploiement : npm run build puis push sur main (GitHub Pages sert directement docs/).

09Ce qui ne se transpose pas

Spécifique UFOLEP GAF, à refaire entièrement pour la FFG :

✕ Ne se transpose pas

  • Tous les regulation/data/**/*.json — arches, éléments, barèmes, évolutions, âges/catégories.
  • Le calendrier scrappé depuis un Google Sheets UFOLEP précis (endpoint gviz/tq?tqx=out:csv).
  • Les CheckSpec concrets de checks.ts — encodent des règles UFOLEP précises.
  • Le modèle Saut à part (engine/saut.ts) — à vérifier si la FFG a un système équivalent.

✓ Se transpose

  • Le type de système : id → CheckSpec → evaluateCheck.
  • L'architecture Firebase (Auth, Firestore, règles de sécurité).
  • Le pattern de partage par lien (instantané figé, collection publique).
  • Export/import JSON, glisser-déposer Pointer Events, structure de fichiers.

10Démarrer le nouveau projet

  1. npx create-next-app (App Router, TypeScript, Tailwind) en reprenant next.config.ts (export statique) si l'appli doit rester 100 % cliente/hébergeable sur GitHub Pages.
  2. Recréer src/regulation/types.ts avec les concepts FFG équivalents (paliers/niveaux, familles, évolutions/catégories — noms exacts selon le règlement FFG).
  3. Construire checks.ts au fur et à mesure que les exigences FFG sont transcrites, pas tout d'un coup.
  4. Copier le pattern Firebase (firebase.ts, AuthContext.tsx, AuthGate.tsx) tel quel, avec un nouveau projet Firebase.
  5. Redemander explicitement où sont les documents/PDF officiels FFG avant d'écrire la moindre donnée réglementaire.
